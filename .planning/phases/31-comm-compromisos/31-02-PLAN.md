  body (campo NUEVO, opcional, aditivo):
    commitment: { tipo, parte?, canal?, motivo?, dueAt? } | undefined

  `lead.commitment` y `lead.nextAction` viajan dentro de `lead`.

PATCH /api/setters/leads/:id/commitment    (auth: requireAuth)
  body A (crear/reemplazar): { tipo, parte?, canal?, motivo?, dueAt? }
  body B (cerrar):           { estado: 'cumplido' | 'incumplido' | 'vencido' }
  respuestas:
    200 { ok:true, commitment, nextAction, lead:{id, ...lead} }
    400 { error } — ni `tipo` válido ni `estado` válido en el body
    403 { error } — setter que no es dueño / lead fuera de visibilidad
    404 { error } — lead inexistente
    409 { error } — crear sobre un lead terminal, o cerrar sin compromiso pendiente

En `call-disposition` un payload inválido se ignora en silencio (nunca 4xx, D-01 de la Phase 30). Test dedicado con campos extra desconocidos. |

Verificado por test de 403 y por mutación del guard. |
| T-31-03 | Spoofing | `body.nextAction` | mitigate | `_gateSanitizeNextActionOverride` queda intacto (fuerza `origen:'manual'`): la única vía de escribir `origen:'compromiso'` es el sanitizador del compromiso. Acceptance criterion de diff vacío en ese rango. |
