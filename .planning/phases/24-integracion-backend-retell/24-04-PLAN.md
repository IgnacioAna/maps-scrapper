### Decisión de implementación: HMAC nativo, sin instalar `retell-sdk`

D-24-06 dice: *"si el SDK Node es instalable, usarlo; si no, replicar su verify
leyendo su source"*. La research YA leyó el source (§2.1, `lib/webhook_auth.mjs`
de `retell-sdk@5.53.0`, citado verbatim) y el algoritmo resultó ser HMAC-SHA256
con una concatenación de timestamp — 6 líneas con el `crypto` que el archivo ya
importa. Se toma la segunda rama de la decisión:

- Cero dependencias nuevas (el proyecto tiene 7 en total y ninguna nueva en años).
- El audit de legitimidad del research marcó `retell-sdk` como `[ASSUMED]`
  (slopcheck no pudo correr por SSL del entorno) → instalarlo obligaría a un
  checkpoint humano bloqueante para verificar el paquete, por una función de 6
  líneas.
- Los tests firman con el mismo primitivo, sin depender del paquete.

Si en el futuro el formato de firma cambiara, el swap al SDK es de una línea, y
en ese momento sí corresponde el checkpoint de legitimidad.

Firma de Retell (research §2.1, source real del SDK):
- Header: `x-retell-signature` (lowercase en Express).
- Formato: `v={timestamp_ms},d={hex}` — regex `^v=(\d+),d=([0-9a-f]+)$/i`.
- Se firma: `HMAC-SHA256(rawBody + String(Number(timestamp)))` con el API key
  como secret. El timestamp va DENTRO de la firma, no en un header aparte.
  ⚠️ El SDK hace `input + poststamp` donde `poststamp = Number(match[1])` — para
  matchear bit a bit hay que concatenar `String(Number(m[1]))`, no el string
  crudo del match (difieren si vinieran ceros a la izquierda).
- Ventana: 5 minutos (`Math.abs(now - poststamp) > 300000` → rechazar).
- Comparación en tiempo constante: `crypto.timingSafeEqual` sobre Buffers,
  chequeando longitud igual antes (`timingSafeEqual` tira si difieren).

Shape del request de la custom function (research §2.2.b):
`{ name: 'book', call: { call_id, agent_id, call_status, metadata,
retell_llm_dynamic_variables, transcript, transcript_object }, args: { fecha, hora } }`.
Existe un toggle "Payload: args only" en Retell que manda SOLO `args` en el top
level → el handler debe tolerar las dos formas.
Autenticación: sección "Custom Headers" del function node → header estático
configurado en el dashboard (Phase 26). Retell **NO reintenta** una custom
function que falla o da timeout.
Respuesta: cualquier 2xx; "todo lo que devuelvas se convierte a string y se le
pasa al LLM del agente". No hay schema obligatorio.

Shape del calendarEntry a replicar — index.js:10611-10621:
`{ id: 'cal_<ts>', leadId, fecha (ISO), nombre, calendarioEstado: 'pendiente',
valorProyecto: 0, comision: 0, setterId, sourceCall: true }`.

Política de reintentos del webhook (research §5.3): Retell espera 2xx en **10s**
y reintenta hasta **3 veces**. Idempotencia recomendada por Retell: `event + call_id`.
